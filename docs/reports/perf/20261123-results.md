# Performance results: A, B, savepoint setting, C1, C2 (2026-11-23)

Before/after for the work chosen from [20261123-baseline.md](20261123-baseline.md). Same harness (`benchmark/perf/compare.rb`), same machine, same method. Units: **µs per call, lower is better**. "factory_bot" is the same library measured in the same run, so its value moves only by noise.

What changed, in commit order on `mohd/perf`:

| step | change | commit |
|---|---|---|
| A | one RNG per bake shared with FFaker; plugin DSL included once per builder class; `scope_for_create` once per collection | `190b2d6` |
| B | `created_at`/`updated_at` left to ActiveRecord (behavior change) | `190b2d6` |
| savepoints | `FactoryBakery.savepoints`, default `false`; gates the `bake!` wrapper and fallback attempts only | `762183a` |
| C1 | plain uniqueness validator checked with one `exists?`; validator lookup memoized | after `762183a` |
| C2 | a `bake!` root leaves its uniqueness check to its own `save!`; retry on a taken generated value | `0173f61` |

## What each step bought (SQLite, µs)

- **A (RNG, DSL, scope):** the largest share of the flat-model gain (186 → about 135 together with B). Allocations per flat `bake` fell 367 → 258.
- **B (timestamps):** about 23 µs per record; 60 µs on a three-record chain.
- **Savepoint setting:** 5–13% on the scenarios that open the gated savepoints (`bake!`, fallback). The associations plugin's edge savepoints are not gated (see below).
- **C1:** validated `bake` 364 → 330 (−9%) from skipping the record copy and the validator's errors object, and memoizing the validator lookup.
- **C2:** validated `bake!` 612 → 452 (−26%) on SQLite, 1144 → 995 on Postgres, from dropping one of the two identical SELECTs.

## Correctness

- `bundle exec rspec`: 1430 examples, 1 failure that predates this work (`spec/factory_bakery/sequel/registration_spec.rb:16`, Ruby 4.0 `logger` no longer a default gem). Regex-generation coverage is 100% line and branch (390/390, 84/84).
- Real-app smoke with definitions, four passes (A–D), through each app's `Gemfile.perf` (the worktree), final code `0173f61`:
  - **Mastodon: 123/123 in all four passes.**
  - **Discourse: 413/413 in passes A, B, D and 412/413 in C.** The one failure is `Chat::NullUser` ("Primary email can't be blank"). It fails identically on the untouched base `bbb0185` and passes on the other agent's snapshot `e6a27c2`, so it comes from the base, not this work, and should clear on the merge onto `mohd/v0.0.2`. The required 413/413 in C is therefore **not yet met on this branch**.
- Pass D flakiness: after C1/C2 landed, four runs of Discourse pass D failed twice, on two different models (`Boards::Card`, a unique-index violation on `(board_id, acting_user_id, created_at::date)`; `PostReply`, a duplicate `(topic_id, post_number)`). The shared Redis was becoming unresponsive around then. Afterwards, nine pass-D runs (three each with C1+C2 off, C1 only, and both on) and a final full four-pass run were all 413/413, and the base ran 4 for 4 clean. I could not reproduce either failure, so the cause is **not established**. Both failures are database unique indexes the gem does not generate values for, and neither involves a uniqueness validator C2 defers. If it recurs, the first suspects are B (creation timestamps are now "now", so per-day unique indexes can collide where random past dates used to avoid it) and the shared Redis.

## What changed for users

All in `CHANGELOG.md` under *Performance*:

1. **Values for a seed differ** from the previous unreleased build (FFaker and the bake share one generator).
2. **`created_at`/`updated_at` are no longer generated** when ActiveRecord manages them (unsaved `bake` leaves them `nil`, `bake!` stamps now). A validated timestamp, or a model with `record_timestamps = false`, is still filled.
3. **`FactoryBakery.savepoints` defaults to `false`**: a failed `bake!` and the verified fallback no longer roll back what a declaration block or FK-presence edge saved earlier. `true` restores that. The associations plugin's best-effort edges keep their savepoints either way, because on PostgreSQL a failed statement outside a savepoint aborts the transaction (the Mastodon smoke hit exactly that when they were gated).
4. **A `bake!` root defers its uniqueness query to `save!`** and retries a taken generated value (ADR-0002 amendment).

## Remaining gap and what is left

The largest remaining gap is validated `bake` (unsaved): 6.7x on SQLite, 6.4x on Postgres. The time is the uniqueness probe (still one query per unique column, since an unsaved bake has no save to defer to) and regex synthesis. Options not yet taken, with estimates from the baseline profile:

- **Share a parent per class within a bake (D):** about 3x on Discourse `Post`; touches association target resolution, so after the `mohd/v0.0.2` merge.
- **Compile each regex's generation plan once** (`Window` allocations are ~50 per call): estimated 5–8% of validated `bake`.
- **Cache the required-ness partition per class** for attributes without conditional rules: about 5%.
- **Fill optional columns in place instead of the fallback's second full build:** removes the 85% penalty on models that fall back; behavior-sensitive.
