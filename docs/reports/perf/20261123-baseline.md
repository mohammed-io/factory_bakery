# FactoryBakery performance baseline (2026-11-23)

How fast FactoryBakery is, how it compares with factory_bot, where the time goes, and what to fix first. This report is new and stands alone: it does not build on `docs/reports/profiling-20261119.md`.

- **Code measured:** branch `mohd/perf` at `bbb0185` (based on local `mohd/v0.0.2`). The gem was not changed. Ablations were in-process monkeypatches in a scratch script.
- **Real apps:** gem snapshot `.smoke-tests/gem-9ffa0bb`, which is now checked out at `e6a27c2`. Another agent moved it, not this work.
- **Machine:** Apple M2 Pro (12 cores), 32 GB RAM, macOS (Darwin 25.5). Other agents were running jobs at the same time (load average about 4), so wall times carry ±5–20% noise. Allocation counts, SQL counts and `valid?` counts are exact.
- **Synthetic stack:** Ruby 4.0.1, ActiveRecord 8.1.4.1, factory_bot 6.6.0, benchmark-ips 2.14, stackprof, vernier 1.12, memory_profiler 1.1. Databases: in-memory SQLite 2.9, and PostgreSQL 18.4 on localhost (its own scratch database `factory_bakery_perf`).
- **Real-app stack:** Ruby 3.4.3, Mastodon and Discourse test environments on the smoke Postgres (port 55432). Runs were taken only while no other smoke job was running.

## How to reproduce

```sh
bundle exec ruby benchmark/perf/compare.rb                         # SQLite
DATABASE_URL=postgres://postgres@localhost:5432/factory_bakery_perf \
  bundle exec ruby benchmark/perf/compare.rb                       # Postgres
bundle exec ruby benchmark/perf/profile.rb validated_build all     # stackprof wall+object, vernier, memory_profiler
```

`benchmark/perf/support.rb` holds the schema, the equivalent factories for both libraries, and the probes. `PERF_ONLY=flat_build,chain_create` limits the scenarios. Profiles go to `tmp/perf/`. The factory_bot comparison gems live in a `:benchmark` Gemfile group, never in the gemspec.

### Method

- **Same schema, equivalent factories.** factory_bot gets literal values plus `sequence` for unique columns, which is its best case. FactoryBakery gets nothing (heuristics), except in the "definition" rows, where it gets the same values factory_bot sets.
- **Transactional-test isolation.** Each call runs inside a transaction opened the way Rails' transactional fixtures open theirs: `begin_transaction(joinable: false, _lazy: false)`, rolled back afterwards. This matters. My first harness used a plain `transaction do … end`, and Rails turned FactoryBakery's nested `requires_new` blocks into free `RestartParentTransaction`s (a nested transaction inside a clean, joinable parent needs no SAVEPOINT). Real suites never get that. Under the fixture-style transaction, every `save!` from either library becomes a real SAVEPOINT/RELEASE.
- **Throughput:** benchmark-ips, 1 s warmup + 2 s measurement per entry. **Shape:** SQL statements by kind (`sql.active_record`, schema and cached queries excluded), `valid?` calls (prepended counter, which includes the one inside `save!`), and allocations per call (`GC.stat(:total_allocated_objects)` over 200 warm calls).
- **Profiles:** taken in steady state (every class cache warmed by 200 calls first), 1500–3000 iterations each.

Scenarios: a flat 2-column model; a validated `Account` (presence, length, format regex, uniqueness ×2 with unique indexes, inclusion, enum); the same with a `define` that supplies every validated value; a `Comment → Post → Author` `belongs_to` chain (`:required_only`); `Library has_many :books` in `:all` with `default_count: 3`; a model whose custom `validate` passes (`valid?` probe only); and a model whose custom `validate` demands an optional column (lean attempt invalid, fallback rebuild).

The Postgres baseline is higher for both libraries because the fixture transaction's BEGIN/ROLLBACK are real round trips (about 70 µs of the factory_bot `build` row is that harness cost).

How to read the two tables:

- **Unsaved bakes carry most of the gap.** `build` is almost free for factory_bot (40–50 µs including the harness). FactoryBakery pays about 140 µs of its own per record on a flat model, and much more when uniqueness probes are involved.
- **Once a row is written, the gap shrinks to 1.5–2.5x.** INSERT, `save!` validation and the SAVEPOINT are shared costs. A `belongs_to` chain under `bake!` writes 3 rows in **one** savepoint (autosave saves the whole graph). factory_bot `create` makes three savepoints, one per `create`.
- **A definition that supplies the validated values cuts validated `bake` by 2.7x** (506 → 190 µs): the uniqueness probes and regex synthesis disappear.

| fallback bake / build | FB / fb | 0 / 0 | 0 / 0 | 0 / 0 | **1** / 0 | 839 / 150 |
| fallback bake! / create | FB / fb | 0 / 0 | 1 / 1 | 2 / 2 | **2** / 1 | 1059 / 320 |

(FB = FactoryBakery, fb = factory_bot.)

- **SQL:** the only extra statements FactoryBakery issues are the **uniqueness probes**, one SELECT per uniqueness-validated heuristic attribute. `bake!` then repeats them, because ActiveRecord's own `save!` validation re-runs the same uniqueness queries (4 vs 2 SELECTs).
- **Savepoints are not a SQL cost.** FactoryBakery opens a nested `requires_new` per `bake!`, per fallback attempt and per auto-built parent, but Rails materializes a savepoint only when a query runs inside it. A discarded lean attempt that ran no query rolls back without any SQL. What remains is Ruby-side transaction bookkeeping, which shows up as `TransactionManager#within_new_transaction` self time (3–11% of samples).
- **`valid?`:** extra validation runs come from the fallback probe (+1 for custom validation), `:all` optional-child verification (+3 for 3 children in `bake`, 10 vs 5 in `bake!`) and the rebuild path.
- **Allocations:** FactoryBakery allocates 2.3–5.6x what factory_bot does per record.

## 2. Where the time goes (flame-graph findings)

stackprof wall mode, steady state, SQLite. Percentages are of all samples, which includes the benchmark harness (about 11 µs per call).

**Flat `bake` (186 µs).** `Random::Base#initialize` alone is **22%** of samples (self time). Every top-level bake builds **three** Mersenne Twister generators: its own (`Randomness.top_level_bake`), one when it reseeds FFaker (`FFaker::Random.seed=` → `new_rng`), and one when it restores FFaker's previous seed. A `Random.new(seed)` costs 12–22 µs on Ruby 4.0 (micro-benchmarked: 11.7 µs with a small seed, 21.6 µs with a 64-bit seed). The rest:

- `heuristic_values` 26%, of which DateTime filling of `created_at`/`updated_at` is 7.7%, the integer filler 7.5% and the string filler 4.8%
- `partition_candidates` 5.1%, `instantiate` 4.4%, `prepare_heuristics` 4.7%, `apply_values` 4.1%
- GC 6%

**Validated `bake` (506 µs).** `UniquenessEnforcer#call` is **43.6%**. Inside it:

- `ActiveRecord::FinderMethods#exists?`: 22.5% (the query itself)
- `Kernel#dup` of the whole record to make a probe copy: 8.8%
- `UniquenessValidator#validate_each` plumbing: the rest

Regex synthesis (`RegexGeneration.generate` for `email` and `username`) is 8%. `Random::Base#initialize` is 8.8%.

**belongs_to chain `bake` (465 µs).** `BelongsToBuilder` nested bakes are 54%, and each parent repeats the full per-bake pipeline. Timestamp filling (`Time.local`, `DateTimeFiller`) runs for all three records. `Module#extend_object` is 1.5% self: `evaluate_declarations` extends every builder instance with the plugin DSL module, which creates a new singleton class per bake.

**has_many `:all` `bake` (771 µs).** `AllAutoBuilder` is 73%. Two parts stand out:

- `TargetBuilder.child_overrides` → `association.scope_for_create` is **10.6%**, recomputed for every child although it is the same for all children of one collection.
- `GraphValidity.invalid?` runs `valid?` on each child: 5.9%.

**Fallback rebuild `bake` (357 µs vs 194 µs for probe-only).** The rebuild is a second full build, which adds about 85%. The discarded attempt raises `DiscardAttempt` through a transaction block: `within_new_transaction` self time is 10.9% here.

**Allocations** (memory_profiler, validated `bake`, per call). The top sites inside the gem:

| allocs/call | site |
|---:|---|
| 33 | `regex_generation/window.rb:11` (`Window.new` per repeat step) |
| 19 | `regex_generation/generator.rb:60` |
| 18 | `attribute_fillers/temporal_arithmetic.rb:71` (`Time.local` rebuild for timestamps) |
| 15 | `bakery_builder.rb:593` (`normalize_keys`) |
| 12 + 9 | `bakery_builder.rb:367` / `:376` (taken-name arrays) |
| 12 + 8 | `active_record_mapper/mapper.rb:457` / `:463` (`validators_on` + `select` in uniqueness lookups) |

Nothing is retained (12 kB over 500 calls), so there is no leak. GC is 3–7% of wall time.

## 3. Ablations (measured gains)

Each candidate fix was applied as an in-process monkeypatch (scratch script, gem untouched). Times are min-of-9 × 1000 calls, two independent rounds, SQLite, µs per call including the 11 µs harness.

| ablation | flat bake | validated bake | validated bake! | chain bake | has_many bake |
|---|---:|---:|---:|---:|---:|
| baseline | 158–161 | 399–408 | 648–668 | 397–407 | 686–702 |
| **one RNG per bake, shared with FFaker** | **132–137** | **375–384** | 624–644 | **376–381** | 684 |
| **include the DSL module once per class** (no per-bake `extend`) | 152–155 | 401–406 | 645–663 | **374–381** | **650–659** |
| **leave AR timestamps to AR** | **135–138** | **370–377** | 622–670 | **332–346** | **599–621** |
| memoize `custom_validation?` per class | 162–164 | 410–412 | 662–677 | 402–416 | 689–706 |
| dup the uniqueness probe once per record | 158–160 | 401–407 | 653–667 | 400–407 | 699–711 |
| **all three bolded fixes combined** (with the two no-ops) | **98–101** | **332–348** | **570–612** | **274–288** | **514–546** |

- The RNG fix saves **20–25 µs per top-level bake**. Nested bakes share the root's generator, so it does not scale with graph size.
- Removing `extend` and leaving timestamps to AR **scale with the number of records** in the graph: −6 µs flat, −25 chain and −40 has_many for `extend`; −23, −60 and −85 for timestamps.
- Combined: **flat −38%, chain −30%, has_many −24%, validated −16%, validated `bake!` −10%.**
- `custom_validation?` and the probe `dup` are **not** worth changing (no measurable effect). They are dropped.

The uniqueness probe path (≈44% of validated `bake`, and both extra SELECTs) is the largest remaining cost and was not ablated: its fixes change behavior, see section 6.

## 4. Real-app numbers

Per-model median of 15 calls, required-only, `:fresh` unless noted, Mastodon/Discourse definitions loaded, each call in a rolled-back savepoint. The scratch spec is `.smoke-tests/real-app-cache/perf_timing_spec.rb` (new file, mine). Raw output: `<app>/perf-timing*.jsonl`. "SQL" counts exclude savepoint statements.

### Mastodon

| model | bake ms (SQL) | bake! ms (SQL) | Fabricate.build ms | Fabricate ms (SQL) |
|---|---:|---:|---:|---:|
| Account | 1.71 (2) | **38.99** (8) | 1.40 | 8.69 (13) |
| Status | 2.49 (2) | 49.67 (11) | 1.51 | 10.67 (16) |
| User | 7.00 (9) | 56.63 (23) | 1.42 | 8.11 (13) |
| Tag | 0.38 (0) | 0.89 (1) | 0.04 | 0.51 (1) |
| Favourite | 5.11 (2) | 108.64 (29) | 2.94 | 22.50 (39) |
| Follow | 4.40 (5) | 73.21 (23) | 2.81 | 18.62 (32) |

`bake` (unsaved) is within 1.2–5x of `Fabricate.build`. `bake!` is 4–6x slower than `Fabricate` **with fewer SQL statements**. The cause is the app, not the gem: `Account before_create :generate_keys` generates a 2048-bit RSA key (about 30 ms), and Mastodon's own fabricator sidesteps it with pre-built keypairs. Every `Account` in a graph pays it: Favourite and Follow build two. A `keypairs`/`public_key` declaration in the Mastodon definitions would remove most of the gap. That is a definition change, not an engine one.

|---|---:|---:|---:|---:|
| User | 7.37 (11) | 14.28 (37) | 10.28 (29) | 4.30 (11) / 13.87 (37) |

| Post | **135.60 (148)** | **154.86 (155)** | 43.75 (56) | **41.01 (18)** / **57.76 (24)** |
| Category | 20.32 (40) | 46.55 (66) | 21.10 (46) | 1.79 (4) / 32.00 (30) |
| Tag | 1.32 (4) | 2.11 (7) | 1.14 (4) | — |

`Fabricate.build` is 0.03–0.42 ms for all five models.

An **unsaved** `bake(Post)` issues 148 statements. The SQL trace shows it inserts 2 users, 2 categories, 3 topics and 2 posts, and runs 40 `watched_words` lookups:

- Post and Topic have no definitions, so required-only auto-build creates a separate fresh User for `post.user` and for `topic.user`. Raw-FK presence edges insert their parents while the graph is being built.
- Each Category's `after_create` creates its "About" topic.

Discourse's fabricator shares one user (`topic { Fabricate(:topic, user: attrs[:user]) }`). With `:reuse_non_unique`, Post drops to 41 ms (18 SQL) for `bake` and 58 ms for `bake!`, within 1.3x of `Fabricate`.

On real apps, **graph shape (how many parents get created and persisted, and the app callbacks they fire) outweighs the gem's per-record overhead by one to two orders of magnitude.**

Aggregate datapoint from earlier smoke runs: the full Mastodon smoke (123 models × 4 passes, definitions) takes 1 min 26–30 s; Discourse (413 models × 4 passes) takes 4 min 38 s – 6 min 11 s.

## 5. Top hotspots

| # | hotspot | where | cost (measured) |
|---|---|---|---|
| 1 | Three `Random.new` per top-level bake (own RNG + FFaker reseed + FFaker restore) | `lib/factory_bakery/randomness.rb:51`, `:85`, `:88` | 22% of flat `bake`; ablation −20–25 µs per bake |
| 2 | Uniqueness pre-check: `dup` the record and run AR's validator, one SELECT per unique heuristic attribute, repeated by `save!` under `bake!` | `uniqueness_enforcer.rb:43-68` → `active_record_mapper/mapper.rb:246-258`, `:531-548` | 44% of validated `bake`; 2 of 4 SELECTs in `bake!`; validated `bake` is 7–10x factory_bot |
| 3 | AR-managed `created_at`/`updated_at` filled heuristically (NOT NULL without a default counts as required) | `required_attribute.rb:13`, `attribute_fillers/datetime_filler.rb` → `temporal_arithmetic.rb:71` | −23 µs per record (flat), −60 chain, −85 has_many |
| 4 | Graph shape on real apps: a fresh persisted parent per edge (no sharing of same-class parents) | `associations/belongs_to_builder.rb`, `fk_parent_persistence.rb` | Discourse `bake(Post)` 136 ms / 148 SQL vs 41 ms / 18 SQL with reuse |
| 5 | Fallback rebuild runs a full second build; discard by exception | `fallback_builder.rb:61-79`, `:102-108` | +85% on a model that falls back (357 vs 194 µs) |
| 6 | `has_many` children recompute `scope_for_create` each | `associations/target_builder.rb:75` | 10.6% of has_many `bake` |
| 7 | Per-bake `extend(scope)` of every builder (new singleton class per bake) | `bakery_builder.rb:188` | −6 µs flat, −25 chain, −40 has_many |
| 8 | Regex synthesis per generated value (`Window` struct per repeat step) | `regex_generation/generator.rb:55-60`, `window.rb:11` | ~8% of validated `bake`, 50+ allocs per call |
| 9 | `:all` optional children each validated (`valid?` per child) | `associations/graph_validity.rb:40` | 5.9% of has_many `bake`; 3 extra `valid?` |
| 10 | Per-bake recomputation of class-stable facts: required-ness partition, taken-name arrays, `normalize_keys`, `mapper_for` | `bakery_builder.rb:472`, `:367-376`, `:593`; `mapper_registry.rb:220` | 5% (partition) + ~2% (`mapper_for` self) + most of the 2.5x allocation gap |

Ruled out: `custom_validation?` memoization (no gain), one probe `dup` per record (no gain), and savepoints as SQL (they stay lazy and never hit the database unless a query runs inside).

## 6. Optimization options

These are the proposals for Phase 2. Nothing has been implemented.

**A. Zero-behavior-change internals.** Hotspots 1, 6, 7 and 10:

- one generator per bake, shared with FFaker by swapping FFaker's generator object instead of reseeding it
- include the plugin DSL module once per builder class
- `scope_for_create` once per collection
- memoize the required-ness partition per class for attributes that are not record-dependent
- fast paths for `normalize_keys` and the taken-name arrays

Expected gain: flat −20%, chain −15%, has_many −15–20%, validated −7%. Allocations −20–30%. Risk: low. One note: for a given seed, generated values will differ from today's (reproducibility within a version is unchanged), so it needs a CHANGELOG line.

**B. Leave framework timestamps to the framework.** Hotspot 3. Expected gain: a further −15% flat, −15% chain, −12% has_many.

This changes behavior. Unsaved `bake` leaves `created_at`/`updated_at` nil (as factory_bot `build` does). `bake!` stores "now" (ActiveRecord's own stamp) instead of a random past time, so specs that relied on old-looking timestamps would change. The values stay reachable through overrides or `fill_optional: %i[created_at]`. Risk: medium. This is a product decision.

**C. Cheaper uniqueness.** Hotspot 2, in two steps:

- **C1 (low risk):** for a plain uniqueness validator (no `scope`/`conditions`/`if`/`case_sensitive: false`, and the column's own class), query `unscoped.where(col => value).exists?` directly instead of `dup` + validator. Same SELECT count. Expected −10–15% on validated `bake` (estimated from the profile; not ablated).
- **C2 (higher risk, needs an ADR-0002 amendment):** under `bake!`, skip the pre-save probe for values with high entropy. Let `save!`'s own uniqueness validation decide, and regenerate-and-retry inside the savepoint on a `:taken` error. That halves the SELECTs in validated `bake!` and is worth about −30% there on Postgres.

**D. Graph shape for real apps.** Hotspot 4. Share one fresh parent per class within a bake when the edges are non-unique (Discourse `post.user` and `post.topic.user`), or make it the documented default for raw-FK presence edges. This is the largest real-app win (Discourse Post 3.3x). It touches association target resolution, which the other agent is changing (`resolve_target`, FK-based targets), so it should wait until that work merges. Risk: medium to high (semantics of `:fresh`).

## Verification state at baseline

`bundle exec rspec`: 1399 examples, 1 failure, 8 pending; regex-generation coverage 100% line (390/390) and branch (84/84). The one failure (`spec/factory_bakery/sequel/registration_spec.rb:16`) predates this work and comes from Ruby 4.0: `logger` is no longer a default gem, and that spec's gem-free subprocess cannot `require 'logger'` (`lib/factory_bakery/seed.rb:3`). `bundle exec rubocop` reports about 190 offenses already present at `bbb0185`; the new `benchmark/perf/` files are clean.

**Recommendation:** do A now. Add B if you accept the timestamp semantics. Do C1 next. Defer C2 and D until after the `mohd/v0.0.2` merge, with ADR updates. Expected result of A + B + C1 on SQLite: flat `bake` about 4.4x → 2.5x factory_bot, validated `bake` about 9.9x → 6–7x, chain `bake` 4.4x → 3x.
