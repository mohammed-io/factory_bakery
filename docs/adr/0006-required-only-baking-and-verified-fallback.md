# ADR-0006: Required-only baking and the verified fallback

- Status: accepted (2026-11-19)
- References: [ADR-0001](0001-framework-agnostic-core-mapper-plugins.md), [ADR-0002](0002-heuristic-first-verified-generation.md), [ADR-0005](0005-condition-aware-constraints.md), [issue #51](https://github.com/mohammed-io/factory_bakery/issues/51)

## Context

Filling every column on a default bake fires side-effecting setters and optional-field validators in real applications (a remote-URL setter that fetches over the network, a guarded `featured_link`, a random value for an enum-like column). Issue #51 changed the default to fill only what a valid record needs. Review of that change found four gaps: `uniqueness` and `comparison` validators were missing from the nil-rejecting set, leaving nullable columns nil and making a second `bake!` fail; Sequel's imperative validation made the fallback unreachable; Rails' autosave validation callbacks made most ActiveRecord models look "custom" and added a `valid?` pass to ordinary bakes; and the fallback rolled back no rows, so a declaration-block parent was inserted twice.

## Decision

1. **Required-only rule.** For each candidate attribute a default bake fills it when the attribute is not column-backed and a public setter plus an applicable validator exist; when a `NOT NULL` column has no default; when a blank default is required by a presence validator; or when a nullable column without a default has an applicable nil-rejecting validator. Everything else keeps its database default or stays `nil` and its setter is never called. `if:` / `unless:` conditions are resolved for the record being baked ([ADR-0005](0005-condition-aware-constraints.md)) and evaluated at most once per (record, validator, attribute) between assignment phases.
2. **The nil-rejecting set.** `presence`, `inclusion`, `format`, `numericality`, `acceptance`, `uniqueness`, `comparison`, and `length` with a positive minimum (or a lazy bound). `allow_nil` / `allow_blank` relax the requirement. Uniqueness is included because Rails queries `WHERE column IS NULL` and treats an existing NULL row as taken; comparison is included because a nil bound cannot satisfy the comparison. Custom `EachValidator`s never force a fill.
3. **When verification runs.** The lean record is probed with `valid?` only when a defaulted, validated column was left unset, or when the mapper reports validation heuristics cannot read: a custom validator, `validates_with`, or a `validate` override. Sequel models with an own `validate` method (where `validation_helpers` declarations live) report true; stored `validation_class_methods` declarations are discoverable and report false. Framework-owned callbacks — the encrypted-attribute guard and `validate_associated_records_for_*` autosave callbacks installed for every association — are not app logic and do not qualify. A mapper that does not implement `custom_validation?` defaults to "verify" rather than silently skipping the check. Otherwise the discovered constraints are trusted and no validation pass is added.
4. **Savepoint per attempt.** Both fallback attempts run inside a nested savepoint obtained through the persistence adapter ([ADR-0001](0001-framework-agnostic-core-mapper-plugins.md)), never through a framework constant in the core. The lean attempt signals discard with a core-defined exception, which rolls its savepoint back before the rebuild; generated-record tracking and `:reuse` graph-cache entries pointing at the discarded graph are dropped as well. The rebuilt attempt runs with `fill_optional` scoped on, so nested parents do not fall back again. Declaration blocks therefore **may run twice** when the fallback fires, and their non-database side effects are not undone.
5. **Opt-in.** `fill_optional` restores the old "fill every column" behaviour globally (`FactoryBakery.fill_optional = true`), per call (`bake(Model, fill_optional: true | false | %i[bio website])`) or for nested bakes. With the opt-in fully on no fallback can happen and no savepoint is opened for it.

## Consequences

- A default bake leaves optional columns untouched, which is what makes remote-URL setters and guarded optional validators harmless; nullable uniqueness and comparison columns are still generated so repeated `bake!` calls and bounded comparisons work without the opt-in.
- Verification is cheap for the common case: a plain `has_many` model is not validated during `bake`, and a model whose rules are all discoverable is not either. The probe runs for genuinely unreadable validation or a defaulted validated column.
- A fallback discards every row the lean attempt wrote, including parents saved by declaration blocks and FK-presence edges, so `bake!` leaves exactly one copy of each. Because Ruby blocks are re-executed, declaration blocks must be safe to run twice when they can trigger a fallback; use call-site overrides or a guard if a side effect must happen once.
- Validator conditions are no longer re-evaluated half a dozen times per bake, but they are re-evaluated after each assignment phase because a guard may read an override. Results stay fiber-local and never cross a top-level bake boundary.
- Adding a mapper requires deciding whether its validation logic is introspectable; the conservative default means an unfamiliar mapper verifies more rather than less.
